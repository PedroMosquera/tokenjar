# Tokenjar design

Tokenjar is a personal macOS menu bar app that answers one question at a glance: how much room is left on each AI subscription before the next limit, and will the current pace run out before the window resets.

It is an alternative to CodexBar that you build from source, so no third-party binary handles your AI credentials.

This is the design of record. Each section describes the code on `main`, and a change that alters one of these rules updates this page in the same commit. [privacy.md](privacy.md) is the exact list of what the app reads, runs, contacts and writes.

## Goals

- Show every limit window each account reports (5-hour, weekly, weekly per model, monthly), as used %, with a reset countdown and a pace marker.
- Show money only where it exists: Claude extra usage and OpenCode Zen's local spend this month. Codex credits are not dollars, so they appear as a note ("Credits: 125.5" or "Credits: unlimited").
- Keep a local history so charts show utilization over time and API-equivalent cost per day, model, harness, project and account.
- Several accounts per provider (for example a personal plan and a company seat on the same Mac).
- Open each provider's own usage page in one click.
- Per-account settings, alerts, and a secret-free config file that syncs through the dotfiles repo.

## Non-goals

Widgets, iCloud sync, browser cookie import, embedded web views, auto-update feeds, telemetry, plugins, status-page polling, currency conversion, and any provider beyond Claude, Codex, OpenCode and Google Antigravity.

## Hard rules

These are the reason the app exists, so they are enforced in code and covered by tests.

1. **The app never reads, stores, or refreshes an OAuth token.** Claude, Codex and Antigravity usage comes from their own CLIs (`claude -p /usage`, `codex app-server`, `agy -p /usage`). Those CLIs own their credentials and their refresh. Refreshing a CLI-owned token from another process rotates a single-use refresh token and logs the CLI out.
2. **The app never touches the Keychain items of other apps.** Its only Keychain use is its own item, service `com.pedromosquera.tokenjar.apikeys`, for API keys the user pastes in Settings.
3. **One outbound endpoint.** The only HTTP request the app makes itself is `GET https://opencode.ai/zen/go/v1/usage`. `HTTPClient.allowedEndpoints` lists exact paths per host. `HTTPClient.validate` rejects any other scheme, host, path or port, and any query, fragment or user info. `URLSessionTransport` checks again, refuses every method but GET and never follows a redirect. `HTTPClientTests.allowlistIsExactlyOpenCode` fails if the list changes.
4. **No content leaves a local file.** History scanners decode only numeric usage fields, model ids, timestamps, the last path component of the working directory, and the ids that keep each response counted once. The store keeps those ids and the log paths only as SHA-256 digests. Prompts, outputs, emails and account ids are never stored, logged or displayed.
5. **No mutating calls.** Nothing the app sends may spend a reset credit, send an email, start a model turn, or onboard a project. A CLI update can still make `/usage` run as a model turn. The [probe latch](#probe-latch) then stops every probe of that account until the CLI's binary changes or the user clicks Try once more.

Codex `account/read` must never be sent with `refreshToken: true`, and the app never uses the codex consume or nudge methods.

Each fetcher conforms to `UsageFetcher` and returns a `UsageSnapshot`: a list of `UsageWindow`s keyed by a stable id, money lines, plan, source and notes. Ids: `session` (5-hour), `weekly`, `weekly:<model>` (Claude per-model weeks) and `monthly` (OpenCode Go). Codex adds `<minutes>m` for other window lengths, `<limitId>:<id>` for extra limits such as `codex_spark:weekly`, and `spend-cap`. Antigravity uses `<pool>:session` and `<pool>:weekly` per quota pool (for example `gemini:weekly`). A Claude limit kind Tokenjar does not recognize keeps its raw kind in the id, and an unknown Antigravity window keeps its name reduced to letters and digits. Windows are keyed by duration or kind, never by position, because Codex Pro has no 5-hour window; only a Codex window with no reported length falls back to `primary` or `secondary`. The ids also key `window_samples` and alert state, so they must not change.

## Architecture

SwiftPM package, Swift tools 6.2, macOS 14 or later, built with Command Line Tools only (no Xcode).

- `TokenjarCore` (library, no UI, links `sqlite3`): models, fetchers, history scanners, SQLite store, pace math, alert engine, config, pricing, process runner, HTTP client, account discovery, CodexBar import, Settings rules and the sign-in command. Everything testable lives here.
- `Tokenjar` (executable, default isolation `MainActor`): AppKit `NSStatusItem` + `NSPopover` hosting SwiftUI, plus AppKit-owned windows for Dashboard and Settings (`WindowPresenter`). AppKit owns the windows because SwiftUI's settings opener is unreliable for accessory apps on macOS 26. While one of them is open the app switches to the regular activation policy so the window comes to the front, and back to accessory when the last one closes.
- `AppModel` is the single source of truth. Views read it and call its actions; they never fetch on their own. `FetcherRegistry` maps each provider to its fetcher and history scanner.

## Scheduling

`AppModel` ticks every 30 seconds. `RefreshScheduler` decides which accounts are due, and is pure so its rules are tested without spawning a CLI.

- An account is due once its interval has passed since its last result: the account's `refreshMinutes`, else the global one (default 10), at least 30 in Low Power Mode, and never below 1.
- Forced refreshes skip the interval: launch, 8 seconds after wake (ticks pause from sleep until then, so nothing fetches before the network is back), opening the popover when the last refresh is 2 minutes old or more, and the popover's refresh button.
- After a 429 the account waits the longer of `Retry-After` and twice its interval. Ticks, forced refreshes and edits respect that backoff, with one exception: a result that arrives after its account was edited is dropped and the account is fetched again at once, even when that result was a 429 or a backoff was in place.
- A per-account check (a card's Retry, Settings' Test, Try once more) skips both the interval and the backoff, and checks only that account.
- A pasted key is read from the Keychain at its account's first check after launch and held in memory (`SessionSecretStore`) until the app quits, whatever that read found, so a Deny is never asked again in the background. Only the account's own check reads it again, and only while no key is held. Save Key replaces the held key and checks the account at once.
- No account is fetched twice at once. An account edited in Settings, or changed by an outside edit to the config, is due at once. A result that arrives after its account was edited, disabled or removed is dropped; an edited account that still shows is then fetched again at once. A model-turn failure is never dropped, because the tokens are already spent, and it always latches.
- History is scanned off the main thread at launch and then every 5 minutes, at utility priority. A scanner's checkpoints move only after its events are stored, and one unreadable source does not stop the others.

## Information layout

**Menu bar.** Only accounts with `showInMenuBar` count. Three modes (`menuBar.mode`):

- `worst` (default): Tokenjar's own mark (a ceiling over three rising bars, never a provider logo, which would look like that provider's own menu bar app) plus the tightest used % of the account with the least room left (highest severity, then highest used %). Monochrome while healthy, amber at `menuBar.warnAt` (default 80 %) or when any window is projected to run out (at least 50 % used, at least 10 % elapsed, ETA 15 minutes or more before reset), red at `menuBar.criticalAt` (default 95 %). At 100 % the number becomes the reset countdown (`showResetCountdownWhenFull`, on by default).
- `bars`: one thin bar per account, filled to its tightest window. Bars take severity colors when any account is not healthy, and are dimmed when stale or failing.
- `icon`: Tokenjar's mark only, tinted by the worst state.

Data older than twice the account's refresh interval is drawn at half opacity, and a dot on the logo means the last check failed. With no data yet the item shows a neutral gauge. The tooltip lists every menu bar account with its tightest window and reset countdown.

**Popover (360 pt).** Header: a one-line summary (the account closest to a limit and its window, then "Also:" with other accounts that need a look; or "All clear · next reset in ..."; or "N accounts need attention"), "Updated 2m ago", and a refresh button (Command-R). A config or history problem shows as a banner under it. One card per account in config order; order never changes by severity, color carries it. A card has the colored logo, provider name, label and plan pill (each hidden when it repeats the one before), a clock badge when stale, and a menu: Open Usage Page, Open Status Page (Claude and Codex), Show in Dashboard, Settings for This Account. Clicking the card title opens the usage page. Each window is a bar with a pace tick, its label and "62% · 1h 48m" (used % and time to reset), or "not started". Below the bars come one verdict line for the card's most urgent window, a small burn-up chart, money rows ("$12.40 used of $100.00", one precision for both numbers) and the snapshot's notes. A failed check shows its message with the buttons listed under [Charts and verdicts](#charts-and-verdicts). Cards scroll past 540 pt. Footer: Dashboard (Command-D), Settings (Command-,), Quit (Command-Q).

**Dashboard window.** Sidebar: All accounts, then each account shown on this Mac with its tightest used % as a badge. Header: account name and plan, source and last update, an Open Usage Page button, and the range picker (24h, 7d, 30d). Cost tiles for today, the last 7 days and this month, plus tokens and requests in range. For one account, a tile per window with its pace tick, countdown and verdict. Then "Limits over time", "Daily spend" grouped by model, harness or project (and account in All), and "Top projects". An account that keeps no local logs (Antigravity) gets a note instead of the cost tiles and history cards, and an account whose snapshot has no windows (OpenCode Zen) gets no limits card.

**Settings window.** General (launch at login, refresh interval, menu bar mode with amber and red thresholds, config file path and its link target, Reveal in Finder, Reload, Import from CodexBar). Accounts, grouped by provider; per account: status, Test, Open Usage Page, enabled, label, show in menu bar, id, profile folder for Claude and Codex, API key source for OpenCode, the sign-in command with Copy Command and Sign In in Terminal, refresh and threshold overrides, usage page URL, Remove Account. Alerts (on or off with how alerts are delivered, thresholds, the three extra alert kinds). About (a short summary of what the app runs, reads, contacts and writes; [privacy.md](privacy.md) is the full list).

## Charts and verdicts

- **Severity** is one scale for every surface: accent color while healthy, orange for a warning, red for critical. A window is a warning at `warnAt` or when it is projected to run out (the amber rule above), and critical at `criticalAt`.
- **Verdict.** Every window with a pace gets a kind: "Limit reached, resets in ..." at 100 %, "Runs out ~40m before reset" under the amber rule, "Ahead of pace +N%" or "Under pace -N%" outside a 5-point band, else "On pace". The card shows the most urgent kind, then the higher severity, then the higher used %. A run-out or full verdict is at least a warning, so a "Runs out" or "Limit reached" line always has an orange or red icon. Other verdict lines stay gray, so a bar can be orange at `warnAt` while the line reads "On pace". Dashboard tiles show their own window's verdict, except for a full window.
- **Burn-up chart.** Used % over the current cycle against an even-pace diagonal from 0 at the cycle start to 100 at the reset. It shows the window the verdict judges when that window lasts a day or more, else the weekly window, else the longest. Samples whose own reset belongs to the previous cycle are left out, and the line ends at the live value.
- **Limits over time.** One line per window for one account. For All, one line per account: its tightest window among those long enough to draw as a line at that range, else its tightest. Dashed rules mark the warn and critical thresholds, faint vertical rules mark resets, and a window with more than 12 resets in view drops its markers. A window with more than 12 cycles in the range (a 5-hour window at 7d or 30d) draws one dot per cycle, its peak, instead of a line. Samples are thinned to the peak of each 30-minute (7d) or 2-hour (30d) bucket plus the latest one, and a line breaks across a gap in sampling.
- **Colors.** Each account keeps one color slot in both dashboard charts, in config order with accounts that report windows first, so a spend-only account never leaves a gap between lines.
- **Daily spend** keeps the 6 costliest groups and folds the rest into "Other", unless only one group would fold. Models with usage but no price and no recorded cost are listed under the chart. **Top projects** shows 8, by cost with unpriced projects last, then by tokens. "24h" history covers today and yesterday, because usage is stored per calendar day.
- **Error buttons.** CLI not found: Setup (opens the account's Settings). Signed out: Sign in (opens the account's Settings, where Sign In in Terminal runs the provider's own login). Credential rejected: Settings. Network error, timeout, rate limit or unreadable output: Retry, for that account only. A probe that spent tokens or quota: Try once more and Disable. Anything else: no button.

## Pace

Linear since window start. `elapsed = window - (resetsAt - now)`, `expected = elapsed / window * 100`, `rate = used / elapsed`, `eta = (100 - used) / rate`. Hidden until 5 % of the window has elapsed, and for windows that have not started, report no length or reset time, or reset in the past or more than one window away. The "Runs out" verdict, the amber color and the projected-exhaustion alert all need at least 50 % used, at least 10 % elapsed and `resetsAt - now - eta` of 15 minutes or more.

## Alerts

Projected exhaustion, window reset and source problem alerts each have a toggle under `alerts` (`projectedExhaustion` and `sourceProblems` on by default, `windowResets` off); `alerts.enabled` turns every alert off.

- Threshold crossings, default 80 % and 95 % used, per window; an account can set its own (`alertThresholds`). Only the highest newly crossed threshold fires, and it withdraws the lower one's notification. Dedupe key is account, window, cycle and threshold; the cycle is the reset time rounded to 10 minutes when first seen (the poll time for a window with no reset time). A new cycle starts when the reset time jumps forward by more than half the window or used % drops by 30 points or more; it withdraws the old cycle's notifications and re-arms every alert for that window.
- Projected exhaustion, once per cycle, when the window is at least 50 % and below 100 % used, at least 10 % elapsed, and the ETA is 15 minutes or more before the reset.
- Window reset, only when the last used % Tokenjar saw before the reset was 80 % or more.
- Source problem (CLI missing, signed out, no subscription, credential rejected, unreadable output, unsupported CLI, a probe that spent tokens or quota), once per failure episode, withdrawn on the next success. Network errors, timeouts and rate limiting never open an episode. No emails, ids or raw errors in the text.
- Not-started windows never fire a threshold or projection. They can still get a reset alert, because OpenCode Go reports a window that just reset as not started. Windows whose reset time has passed are skipped.
- An account's first successful poll after launch, and any failure before it, only record a baseline. The one exception is a probe that spent tokens or quota (the Claude or agy model-turn error): it notifies at once, before any baseline, because the latch stops further probes and there would be no later chance to say so. It still needs `alerts.enabled` and `alerts.sourceProblems`, and it is still once per episode, so an account with a source problem already open, even since before a relaunch, gets no new notification. A run of network errors or timeouts does not open one.
- With alerts off the state is still tracked, so turning them on does not replay old crossings. State persists in `alert-state.json` (everything except the baseline set), so a restart does not repeat alerts.

Delivery: notification ids are the dedupe keys, so a repost replaces instead of stacking, and notifications are grouped per account. A click on a notification, or its "Open dashboard" action, opens the dashboard on that account. With alerts on, the app asks macOS only for quiet provisional delivery (no prompt), at launch and when alerts are turned on. The system prompt for banners appears only from "Allow Banners" in Settings > Alerts. Notification Center serves only an app bundle, so a binary run from `.build` cannot post at all.

## Probe latch

`claude -p /usage` and `agy -p /usage` are meant to answer locally. If one runs as a model turn instead, the fetcher throws that CLI's model-turn error, and `ProbeLatch` records the account in `probe-latch.json` with the CLI and a fingerprint of its binary (SHA-256 of the resolved path, size and modification date).

- Claude: the read stops at the first `assistant` line with `usage_report` (the answer) or the first `result` line with `num_turns` or `total_cost_usd` above 0 (a model turn). If it reaches the end without either, any `assistant` line that carried neither `usage_report` nor `local_command_run` makes the run a model turn. A run that times out or exits without a result line after such a line fails the same way, with no cache fallback. A timeout after only the local `/usage` answer is a plain timeout with the cache fallback.
- Antigravity: a top-level `response`, `stats` or `num_turns` in the output of a run that exited 0, when that output has no `groups` and no `error`.
- A latched account is skipped by every path: ticks, wake, popover open, the refresh button, Retry, Settings' Test, and a relaunch, since the file persists. Its card shows the latching CLI's message.
- It is released when that CLI's binary fingerprint changes (a claude update never releases an agy latch, or the reverse), or by `AppModel.retryProbe(accountID:)`, which runs one check and latches again if it repeats. The popover's "Try once more" and Settings' "Try Once More" call it; "Disable" sets the account's `enabled` to false.

## Config and sync

`~/.config/tokenjar/config.json` (`$XDG_CONFIG_HOME/tokenjar/config.json` when that variable is set in the app's own environment) holds non-secret settings: `version`, `refreshMinutes`, `menuBar` (`mode`, `warnAt`, `criticalAt`, `showResetCountdownWhenFull`), `alerts` (`enabled`, `thresholds`, `projectedExhaustion`, `windowResets`, `sourceProblems`), `cliPaths`, `launchAtLogin`, and `accounts` (`id`, `provider`, `label`, `enabled`, `profileDir`, `credential`, `showInMenuBar`, `refreshMinutes`, `alertThresholds`, `dashboardURL`). Every field but an account's `id` and `provider` may be left out and takes its default. It is safe to stow from the dotfiles repo.

- **Merge.** `config.local.json` next to it holds machine overrides and wins on merge. The merge is deep. `accounts` merge by `id`, field by field, and a local entry with a new id is appended.
- **Hidden accounts.** An enabled account shows only when what it reads exists on this Mac: the profile dir (default `~/.claude` or `~/.codex`) for Claude and Codex, and for OpenCode the credential file, else the default `auth.json` (`$XDG_DATA_HOME/opencode/auth.json` or `~/.local/share/opencode/auth.json`; an OpenCode `profileDir` is not checked). A pasted Keychain key and Antigravity have no file to check and always show. One shared file therefore works on every Mac.
- **Save.** Settings edits only `config.json`, never `config.local.json`. A save copies the leaf fields the user changed onto `config.json` as last read, so a value `config.local.json` overrides on a setting or on an account that is in `config.json` never leaks into the shared file, and accounts that exist only in `config.json` are kept. One exception: when any account changes, an account that exists only in `config.local.json` is copied whole into `config.json`. The file is rewritten whole, defaults included, pretty-printed with sorted keys.
- **Symlinks.** A `config.json` that is a symlink is written through its real target, resolved with `realpath`: a relative stow link resolves against the link's own folder and chains are followed, so the link survives. Every Settings edit first checks both files, so a link whose destination is missing is caught there: the app keeps its settings, saves nothing and shows "config.json is missing or its link is broken". `ConfigStore.write` also refuses such a link: it throws `ConfigError.brokenLink`, writes nothing and keeps the link. Any write that fails shows "Could not save config.json."
- **Load errors.** An unreadable file or invalid JSON (merge-conflict markers, a wrong type) in either file throws `ConfigError.invalidJSON` naming that file. The app keeps the settings it last loaded (none, when the load at launch fails), shows "Could not read <file>. Using the last good settings, and nothing is saved until it is fixed and reloaded." ("No settings are loaded" in place of "Using the last good settings" when nothing has loaded yet), and saves no edit until a load succeeds. A `config.json` that goes missing while the app runs, or a stow link whose target is gone, keeps the current settings the same way.
- **Reload.** Each tick compares the modification dates of both files (through symlinks) and reloads on a change, for example after a `git pull` in the dotfiles repo. Every Settings edit checks the same first, so an outside change is the base of the edit instead of being reverted. Settings > General > Reload loads on demand.
- **First run** happens only at launch, and only when nothing at all, not even a dangling stow link, is at the config path. It writes default settings plus the accounts discovery finds: `~/.claude` (labelled Work for a Team or Enterprise `oauthAccount.organizationType` in `~/.claude.json`, else Personal), `~/.codex/auth.json` (existence only), the `opencode-go` and `opencode` entry names in opencode's `auth.json` (Zen is added with `showInMenuBar: false`), and `agy` on the CLI search path. CodexBar's settings are never read at first run.
- **CodexBar import.** Settings > General > Import from CodexBar reads CodexBar's enabled providers, global warning thresholds (CodexBar stores % remaining, Tokenjar % used), refresh interval and notification toggle, lists the changes, and applies them only when the user confirms.
- **CLI paths.** `cliPaths` maps a CLI name to an absolute path. When one is set, that path is the only one tried. Otherwise a fixed list of folders is searched, never through a login shell.

## Storage

`~/Library/Application Support/Tokenjar/` is created, or tightened if it exists, at 0700. `tokenjar.sqlite` in it is created 0600 before SQLite opens it and uses WAL; its `-wal` and `-shm` files take the same mode. `schema_version` records which entries of `SQLiteUsageStore.migrations` have run. Migrations are append-only, and a database newer than the build is refused.

- `snapshots(account_id, fetched_at, json)`: the latest `UsageSnapshot` per account, shown at launch until the first fetch lands.
- `window_samples(account_id, window_id, ts, used_percent, resets_at)`: one row per fetch per window. A sample identical to the previous one less than 5 minutes later is skipped; rows older than 180 days are pruned on the first successful fetch after launch and then at most once a day.
- `usage_events(dedupe_key, ts, account_id, harness, model, project, input, output, cache_read, cache_write_5m, cache_write_1h, reasoning, reported_cost)`: one row per model response, upserted by `dedupe_key` keeping the larger value of each count. `dedupe_key` is the SHA-256 hex digest of the raw key (`claude:<message.id>:<requestId or sessionId>`, `codex:<response_id>`, `codex:<rollout file name>:<cumulative total>`, `codex:<rollout file name>:@<byte offset>`, `opencode:<message id>`). `project` is the last path component of the working directory, `~` for the home folder itself, in all three scanners. A Claude Code worktree (`<repo>/.claude/worktrees/<name>`) or a tool folder inside a repo (`<repo>/.superpowers/sdd/<plan>`) counts as `<repo>`; hidden folders directly under home keep their own name. Raw events rather than rollups, because Claude Code deletes transcripts after 30 days and writes a response on several lines while it streams. Daily totals per local day, account, harness, model and project are computed at query time. The upsert never changes `model` on a conflict.
- `scan_state(scanner, account_id, path, value)`: one checkpoint per log file (Claude, Codex) or per opencode table. `path` is the SHA-256 hex digest of the file path, or of `<opencode.db path>#<table>` for opencode. `value` is `<inode>:<offset>` for Claude, a JSON object with inode, offset and running context (last cumulative totals, model, project) for Codex, and the largest `time_updated` read for opencode.

Migration 2 rewrote every `dedupe_key` an earlier build stored raw into its digest and cleared `scan_state`, which costs one full rescan that merges into the rehashed events. `StoredIdentifierTests.scannedPathsAndResponseIDsAreStoredOnlyAsDigests` runs the real scanners into a real store and checks that the database bytes, WAL included, hold neither the home folder path nor a raw session id.

Next to the database: `alert-state.json` (fired dedupe keys, failing accounts, and the last reset time, used % and cycle per window) and `probe-latch.json` (`{"entries": {"<account id>": {"binary": "<sha256>", "cli": "claude"}}}`, with `cli` either `claude` or `agy` and an entry without `cli` read as claude). Both are written atomically and set to 0600 after the support folder is tightened to 0700.

## Pricing

`Resources/pricing.json` maps model ids to USD per million tokens (input, output, cache read, cache write 5m, cache write 1h), with the source URL and date for each entry. `~/.config/tokenjar/pricing.json` overrides it: each model or alias there replaces the bundled entry of the same id whole, and a file that declares another version, currency or unit is ignored. Costs are labelled "API-equivalent estimate".

- Lookup is the exact id, then an alias, then the normalized id and its alias. Normalizing lowercases the id and drops a `vendor/` path, a Bedrock `[region.]anthropic.` or `openai.` prefix, a `-v1:0` style suffix, a Vertex `@date`, a `[1m]` tag and a trailing release date. Any other id is unpriced rather than borrowing a similar id's price (`gpt-5.5-pro` costs six times `gpt-5.5`); an alias in the override file maps it.
- Claude Haiku 5.5 bills every token of a request at a higher rate once its prompt (input plus cache reads plus 5-minute and 1-hour cache writes) is over 100,000 tokens. `PriceTable.billedModel` records such a request as `claude-haiku-5-5>100k`, Bedrock and Vertex spellings included, and the price table prices that id at the long-prompt rate. It shows as its own model in the by-model split. Events stored before this rule keep `claude-haiku-5-5`.
- Rows whose harness recorded a cost (opencode) keep that cost and are not repriced; only tokens without a recorded cost are priced.

## Distribution

`make install` builds from source with `swift build -c release`, assembles `Tokenjar.app` (Info.plist with `LSUIElement`, bundle id `com.pedromosquera.tokenjar`, version from `VERSION`; the committed `Resources/AppIcon.icns`, `Resources/Logos/` and `Resources/pricing.json` copied in), fails if the binary links an `@rpath` library, clears extended attributes, signs it ad-hoc with the hardened runtime, copies it to `~/Applications` and launches it. `Scripts/make-icon.sh` rebuilds the `.icns` from `Resources/AppIcon.svg` with `sips` and `iconutil`; run it by hand after editing the SVG. No admin rights, no quarantine, no Gatekeeper prompt. The linker gets `-platform_version macos 14.0 26.0` so the binary is stamped with a real SDK version (SwiftPM's default build system stamps the deployment target, which makes macOS run the app in compatibility mode).

**Renamed from Headroom.** Builds before the rename were Headroom, bundle id `com.pedromosquera.headroom`. macOS treats the new bundle id as a new app, so notification permission, the launch at login registration and saved window frames start fresh. API keys pasted in Settings stay under the old Keychain service, `com.pedromosquera.headroom.apikeys`, which the app never reads (hard rule 2), so they are pasted again. `make install` first quits and deletes `Headroom.app` in the install folder, only when its Info.plist names exactly `com.pedromosquera.headroom`; it waits up to 5 seconds for the app to exit and stops without installing if it is still running. History and config move once: `AppModel.loadState` runs `LegacyMigration` before it opens the config or the database, and the developer flags never reach it. It renames `~/Library/Application Support/Headroom` to `Tokenjar` and `~/.config/headroom` (or `$XDG_CONFIG_HOME/headroom`) to `tokenjar` when the new name does not exist yet (a Tokenjar support folder holding only the empty `probe` folder that `--probe` creates counts as absent and is removed with rmdir), then renames `headroom.sqlite` and its `-wal` and `-shm` files to `tokenjar.sqlite*` as one set, putting them back if one rename fails. A rename in place keeps a stow link inside the config folder, or a config folder that is itself a stow link, resolving. When both names exist nothing changes, and nothing moves while an app with the old bundle id, or a process named exactly `Headroom` (the `pgrep -x` match install.sh makes), runs. The move never renames onto a taken name, so while `LegacyMigration.hasDataToMove` still holds afterwards (Headroom runs, or a step failed), `loadState` opens neither the config nor the database and `loadConfig` does nothing for the rest of that launch; the banner says to quit Headroom, or that the move failed, and the next launch tries again. This also covers `make run`, which does not quit Headroom first. A failure is logged and never stops the launch. [privacy.md](privacy.md#renamed-from-headroom) lists exactly what moves.

Constraints found while packaging:

- No `.xcassets` or `.xcstrings` (they need Xcode). Logos ship as SVG in `Contents/Resources/Logos` and load with `NSImage(contentsOf:)` through `Bundle.main`, never `Bundle.module`.
- Command Line Tools ship no SwiftUIMacros plugin, so views avoid the `@State` macro: they use explicit `State` storage, the `SettingsState` alias or an `ObservableObject`.
- Notifications and launch at login work only from an app bundle; use the installed copy in `~/Applications`.
- Ad-hoc signatures change on every build, so Keychain grants for the app's own item re-prompt after a rebuild, and a Deny is not remembered. Only pasted API keys live there, and each is read once per launch (see [Scheduling](#scheduling)).
- On a Mac that only runs approved software, an allowlisting tool blocks every new ad-hoc build until it is allowlisted.

A GitHub Actions release zip and a Homebrew cask are deferred. Homebrew 6 removed `--no-quarantine`, so a cask adds a Gatekeeper prompt without adding anything for a single user.
