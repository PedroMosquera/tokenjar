# Tokenjar design

Tokenjar is a macOS menu bar app that answers one question at a glance: how much room is left on each AI subscription before the next limit, and will the current pace run out before the window resets.

It is an alternative to CodexBar that you build from source, so no third-party binary handles your AI credentials.

This is the design of record. Each section describes the code on `main`, and a change that alters one of these rules updates this page in the same commit. [privacy.md](privacy.md) is the exact list of what the app reads, runs, contacts and writes.

## Goals

- Show every limit window each account reports (5-hour, weekly, weekly per model, monthly), as used %, with a reset countdown and a pace marker.
- Show money only where it exists: Claude extra usage and OpenCode Zen's local spend this month. Codex credits are not dollars, so they appear as a note ("Credits: 125.5" or "Credits: unlimited").
- Keep a local history so charts show utilization over time and API-equivalent cost per day, model, harness, project and account.
- Several accounts per provider, such as two Claude logins on one Mac.
- Open each provider's own usage page in one click, including for a provider that shares no usage yet.
- Per-account settings, alerts, and a secret-free config file that can sync through a dotfiles repo.

## Non-goals

Widgets, iCloud sync, browser cookie import, embedded web views, auto-update feeds, telemetry, plugins, status-page polling in the background, currency conversion, and any provider beyond Claude, Codex, OpenCode, Google Antigravity, GitHub Copilot and Devin (a link only, until Devin has a usage source that fits the hard rules).

## Hard rules

These are the reason the app exists, so they are enforced in code and covered by tests.

1. **The app never reads, stores, or refreshes an OAuth token.** Claude, Codex, Antigravity and GitHub Copilot usage comes from their own CLIs (`claude -p /usage`, `codex app-server`, `agy -p /usage`, `gh api --method GET copilot_internal/user`). Those CLIs own their credentials and their refresh. Refreshing a CLI-owned token from another process rotates a single-use refresh token and logs the CLI out.
2. **The app never touches the Keychain items of other apps.** Its only Keychain use is its own item, service `com.pedromosquera.tokenjar.apikeys`, for API keys the user pastes in Settings.
3. **Allowlisted outbound endpoints.** The app's own HTTP requests are `GET https://opencode.ai/zen/go/v1/usage` and, only while Check provider status pages is on for this Mac, one status summary per tracked provider that has one (`ProviderID.statusFeedURL`): `status.claude.com/api/v2/summary.json`, `status.openai.com/proxy/status.openai.com` and `www.githubstatus.com/api/v2/summary.json`. A status check sends no key, cookie or account data. `HTTPClient.allowedEndpoints` lists exact paths per host. `HTTPClient.validate` rejects any other scheme, host, path or port, and any query, fragment or user info. `URLSessionTransport` checks again, refuses every method but GET and never follows a redirect. `HTTPClientTests.allowlistIsPinned` fails if the list changes. gh's GET to `api.github.com` is gh's own traffic, like every other CLI's, and does not go through `HTTPClient`.
4. **No content leaves a local file.** History scanners decode only numeric usage fields, model ids, timestamps, the last path component of the working directory, and the ids that keep each response counted once. The store keeps those ids and the log paths only as SHA-256 digests. Prompts, outputs, emails and account ids are never stored, logged or displayed.
5. **No mutating calls.** Nothing the app sends may spend a reset credit, send an email, start a model turn, or onboard a project. A CLI update can still make `/usage` run as a model turn. The [probe latch](#probe-latch) then stops every probe of that account until the CLI's binary changes or the user clicks Try Once More.

Codex `account/read` must never be sent with `refreshToken: true`, and the app never uses the codex consume or nudge methods.

Every CLI gets `CLILocator.baseEnvironment`: a few user variables, a fixed `PATH` and `NO_COLOR=1`, plus `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` and their lowercase forms when the app's own environment sets them, so a CLI behind a proxy connects as it does from a terminal. A launch from Login Items or the Finder carries launchd's environment, not the shell's. [privacy.md](privacy.md#commands-it-runs) has the exact list.

Each fetcher conforms to `UsageFetcher` and returns a `UsageSnapshot`: a list of `UsageWindow`s keyed by a stable id, money lines, plan, source and notes. Ids: `session` (5-hour), `weekly`, `weekly:<model>` (Claude per-model weeks) and `monthly` (OpenCode Go, and GitHub Copilot's AI credits or premium requests). Codex adds `<minutes>m` for other window lengths, `<limitId>:<id>` for extra limits such as `codex_spark:weekly`, and `spend-cap`. Antigravity uses `<pool>:session` and `<pool>:weekly` per quota pool (for example `gemini:weekly`). GitHub Copilot uses `chat:monthly`, `completions:monthly` and `<key>:monthly` for any other capped quota, the key lowercased and reduced to letters and digits. A Claude limit kind Tokenjar does not recognize keeps its raw kind in the id, and an unknown Antigravity window keeps its name reduced to letters and digits. Windows are keyed by duration or kind, never by position, because Codex Pro has no 5-hour window; only a Codex window with no reported length falls back to `primary` or `secondary`. The ids also key `window_samples` and alert state, so they must not change.

### GitHub Copilot

`CopilotUsageFetcher` maps the filtered answer like this:

- **Premium allowance.** `premium_models` is the same allowance as `premium_interactions` under a newer name (VS Code reads `premium_models ?? premium_interactions`), so it is used when it carries data, else `premium_interactions`. When capped (not `unlimited`, `entitlement` above 0) it becomes the `monthly` window, labelled "AI credits" when `token_based_billing` is true at the top level or on that snapshot, else "Premium requests". Used % is `(entitlement - quota_remaining) / entitlement * 100`, else `100 - percent_remaining`, at least 0, and at most 100 unless `overage_count` is above 0. A positive `overage_count` adds the note "N AI credits over the allowance this cycle" (or "premium requests").
- **Pooled seats.** An unlimited premium snapshot, or a token-billed one with a zero entitlement (a pooled Business seat can arrive that way without the unlimited flag), has no per-user budget: no window, and the note "N AI credits used this cycle (no per-user limit)" (or "premium requests") from `credits_used`.
- **Chat and completions.** Each becomes `chat:monthly` ("Chat") or `completions:monthly` ("Completions") only when capped. On Copilot Free (`access_type_sku` `free_limited_copilot`), when its snapshot is not capped, the used % comes from `monthly_quotas` (the cap) and `limited_user_quotas` (what is left). No Free account has been probed; this is how VS Code and CodexBar read it.
- **Other quotas.** Any other capped key of `quota_snapshots` becomes `<key>:monthly`, labelled with the key's words.
- **Reset.** `quota_reset_date_utc`, else `quota_reset_date` at 00:00 UTC. Each snapshot's own `quota_reset_at` is 0 in live answers and is ignored. The window length is the UTC calendar month ending at the reset (`UsageWindow.monthMinutes`, shared with OpenCode Go's monthly window), so pace works on 28 to 31 days.
- **Nothing to show.** With no window and no note, the card says "No per-user limits for this account". There is no money line. Source label "gh CLI".
- **Plan.** `copilot_plan`: `free` Free, `individual` Pro, `individual_pro` Pro+, `individual_max` Max, `business` Business, `enterprise` Enterprise, anything else its words capitalized. The individual names are inferred from VS Code's extension.
- **Errors.** gh's exit 4 is signed out. Otherwise stderr is lowercased and matched in this order: "http 429" or "rate limit" backs off (GitHub answers a spent rate limit with 403, so the wording decides first); "http 401" is a rejected credential; "http 403" or "http 404" is "No Copilot access for this GitHub account" (calm, see [Failed checks](#failed-checks)); "http 5xx" and the connection phrases ("error connecting to", "dial tcp", "i/o timeout", "timeout exceeded", "connection reset") are network errors; anything else is unreadable output. A missing gh, or one that cannot start, is CLI not found. Output that is not a JSON object, or has neither a plan nor quotas, is unreadable.

## Architecture

SwiftPM package, Swift tools 6.2, macOS 14 or later, built with Command Line Tools only (no Xcode).

- `TokenjarCore` (library, no UI, links `sqlite3`): models, fetchers, history scanners, SQLite store, pace math, alert engine, config, pricing, process runner, HTTP client, account discovery, the move from Headroom's folders, CodexBar import, Settings rules and the sign-in command. Everything testable lives here.
- `Tokenjar` (executable, default isolation `MainActor`): AppKit `NSStatusItem` + `NSPopover` hosting SwiftUI, plus AppKit-owned windows for Dashboard and Settings (`WindowPresenter`). `StatusItemClick.configure` makes the status item's button send its action on left and right mouse-up and gives it a Show Menu accessibility action, and `StatusItemClick.Router` turns `NSApp.currentEvent` into the popover or the status item menu (`StatusItemMenu`). `StatusItemMenu.open` sets that menu on the status item only while `performClick` shows it, because a status item with a menu opens that menu on every click. The popover's `NSHostingController` uses the `.preferredContentSize` sizing option only, so each change in the content's size reaches NSPopover, which resizes and re-places the popover itself. Under the default options SwiftUI resized the popover's window and NSPopover's `contentSize` did not follow; in a popover window that was never shown, the window grew from a fixed bottom edge, which fits a popover drawn over the menu bar but was not seen on screen. `AppDelegate.open` applies what opening changes (`popoverWillOpen`, the height cap from `PopoverPlacement`) with `layoutSubtreeIfNeeded` and sets the popover's `contentSize` before `show`, because NSPopover places the popover from that size at show and a controller assigned before its first layout leaves it at 0x0. It then scrolls the cards back to the top, also before `show`: the popover keeps one content controller for the app's life, so its scroll view would otherwise reopen where the last open left it. AppKit owns the windows because SwiftUI's settings opener is unreliable for accessory apps on macOS 26. While one of them is open the app switches to the regular activation policy so the window comes to the front, and back to accessory when the last one closes. There is no SwiftUI `App` and so no scene: `TokenjarApp.main` runs `NSApplication` with `AppDelegate`, because a SwiftUI Settings scene opened its own empty window for Command-comma. `MainMenu` builds the menu bar in code, shown while a Dashboard or Settings window is open: the app menu (About, Settings... on Command-comma through the same path as the popover's Settings button, Hide, Hide Others, Show All, and Quit on Command-Q, which asks first like the popover's Quit), Edit (Undo, Redo, Cut, Copy, Paste, Select All, which text fields need for their shortcuts) and Window (Minimize, Close, and the open windows).
- `AppModel` is the single source of truth. Views read it and call its actions; they never fetch on their own. `FetcherRegistry` maps each provider to its fetcher and history scanner.
- `ProviderID` carries what differs per provider: display name, logo, default usage page, status page (every provider but Antigravity, which has no official one), status feed (`statusFeedURL`: Claude, Codex and GitHub Copilot only), harness, `reportsWindows` (false for OpenCode Zen and Devin, which never report a limit window), `checkUsesNetwork` (false for OpenCode Zen, which reads `opencode.db`, and Devin, a link; the two flags match today but answer different questions) and `isLinkOnly` (true only for Devin).

## Scheduling

`AppModel` ticks every 30 seconds. `RefreshScheduler` decides which accounts are due, and is pure so its rules are tested without spawning a CLI.

- An account's next check is its interval after its last check started: the account's `refreshMinutes`, else the global one (default 10), at least 30 in Low Power Mode, and never below 1. It is due on the first tick at most 15 seconds before that time, so a 10-minute account is checked every 10 minutes rather than every 10 minutes 30 seconds.
- Forced refreshes skip the interval: launch, 8 seconds after wake (ticks pause from sleep until then, so nothing fetches before the network is back), opening the popover when the last refresh is 2 minutes old or more, and the popover's refresh button. `lastRefreshAt`, when the last batch of checks ended, is read only by that popover rule; every surface that says "Updated" reads `lastUpdated`, the newest successful check.
- Provider status has its own rule (see [Provider status](#provider-status)): opening the popover asks a provider whose status page was last asked 2 minutes ago or more, answered or not (`ProviderHealth.askAgainAfter`, separate from `RefreshScheduler.popoverRefreshAge`), and the refresh button, Command-R and Refresh Now ask every one. Launch, wake, ticks and a return from offline force account refreshes but never ask a status page, so the status check hangs on `popoverWillOpen` and the user-initiated path, not on `refresh(force:)`.
- After a 429 the account waits the longer of `Retry-After` and twice its interval, counted from that answer. Ticks, forced refreshes and edits respect that backoff, with one exception: a result that arrives after its account was edited is dropped and the account is fetched again at once, even when that result was a 429 or a backoff was in place.
- A per-account check (Retry or Try Again on a card, Check Now or Try Again in Settings, Try Once More) skips both the interval and the backoff, and checks only that account.
- A pasted key is read from the Keychain at its account's first check after launch and held in memory (`SessionSecretStore`) until the app quits, whatever that read found, so a Deny is never asked again in the background. A refused read (`errSecAuthFailed`, `errSecUserCanceled`, `errSecInteractionNotAllowed`, `errSecInteractionRequired`) shows as "Keychain access was denied", never as signed out. Only the account's own check reads it again, and only while no key is held. Save Key replaces the held key and checks the account at once.
- No account is fetched twice at once. An account edited in Settings, or changed by an outside edit to the config, is due at once. A result that arrives after its account was edited, disabled or removed is dropped; an edited account that still shows is then fetched again at once. A model-turn failure is never dropped, because the tokens are already spent, and it always latches.
- **Offline.** `PathMonitorNetworkStatus` reads only the status of macOS's network path (`NWPathMonitor`; `satisfied` and `requiresConnection` are usable, `unsatisfied` is not). Only `AppModel.start` starts it, so renders, developer flags and tests never run one. `NetworkWatch` debounces its reports. From the first unusable report it holds checks: every automatic refresh (ticks, launch, wake, popover open, a dropped result's re-fetch, an edited account) and the popover-open status check leave out the accounts that need the network (`ProviderID.checkUsesNetwork`: all but OpenCode Zen and Devin) before `RefreshScheduler.due`, so they are never begun and stay due. OpenCode Zen, Devin and history scans still run. What the user asks for is never held: the refresh button and Command-R (`userInitiated`), and every per-account check. Checks already running are left to finish or time out. The UI shows offline only after 10 seconds without a usable path, and back online only after 3 seconds with one, so wake, roaming and a path that flickers do not flash it; neither number was measured. Coming back after a declared offline period checks every account once (`force`, which still respects a 429 backoff, a check in flight and the probe latch), at most once every 2 minutes, after which a return checks only what is due. A wake refresh that runs while that return is still owed counts as it. A drop shorter than 10 seconds checks only what it skipped, at once. Between sleep and the wake refresh, reports change only what the UI shows. Time asleep counts toward neither settle: both start over at wake. The launch refresh waits for the monitor's first report, or 1 second without one, so a launch while offline spawns nothing that needs the network. Path status has false positives (a VPN or tunnel macOS calls unusable): when a check that started while the path read unusable gets a live answer from an account that needs the network, and macOS still calls the path unusable, nothing is held and offline is not shown until the monitor's next report. The outage still pushed accounts a full interval out, so the next usable path checks every account as a return from offline does.
- History is scanned off the main thread at launch and then every 5 minutes, at utility priority. A scanner's checkpoints move only after its events are stored, and one unreadable source does not stop the others. The dashboard also loads its history off the main thread.
- The popover keeps its own clock, which moves only while it is shown, so a closed popover does not redraw on every tick; opening it brings the clock up to date first.

## Failed checks

`FetchError.attention` sorts every failure by how much it asks of the user, and the popover, menu bar, dashboard and Settings all read that one classification, so they never disagree about what counts as a problem.

- **Calm**: no subscription (OpenCode Go's 403 or entitlement error, GitHub's 403 or 404 for Copilot). It is an answer, not a fault: a gray minus icon and the message, no button, no menu bar dot, no header warning. Settings says "Not subscribed to <provider>" and the dashboard sidebar captions it "Not subscribed"; an account with no data from before gets no limits card and stays out of the menu bar.
- **Transient**: a network error, a timeout or a rate limit. It never needs attention, however old the data: a gray icon (Wi-Fi for a network error, a clock otherwise) with Retry, Settings adds "Showing data from <age>.", and it draws no menu bar dot, takes no place in the header's "needs attention" count and turns nothing orange. A network error or timeout that leaves an account that needs the network with no fresh data (`AccountStatus.cannotRefresh`; a provider's saved copy shown because of one counts) gets a gray header line that names the provider instead. A rate limit is Tokenjar waiting by choice, so it never reaches the header. It never opens an alert episode.
- **Actionable**: CLI not found, signed out, a rejected credential, unreadable output, an unsupported CLI, a CLI too old to read, a probe that spent tokens or quota, and Keychain access denied. An orange warning icon, the menu bar dot, a place in the popover header's "needs attention" count, and, where one exists, a button that fixes it.

Two causes are Mac-wide rather than one account's (`Connectivity`, recomputed after every path report, settle and check, and only when an account shown needs the network). **Offline**: macOS has reported no usable network path for 10 seconds (see [Scheduling](#scheduling)). **Can't reach any provider**: the path is usable, yet no account that needs the network got an answer in its latest check (a live answer or a rate limit; a saved copy is not one), and at least two different providers failed with a network error or a timeout, counting a saved copy shown because of one; two accounts of one provider count once, and a failure of another kind neither confirms nor blocks it. Only checks that ended since the path last became usable count: a check that failed during a drop, or while the Mac was offline, says nothing about the network that came back. A drop too short to call offline changes neither cause, so a flapping path does not flash the slash. No host is contacted to tell these apart. One provider failing alone stays that provider's problem.

Messages are whole sentences that say what went wrong and what happens next, and never carry raw errors, ids or emails. A surface that shows one account (a card, Settings, the dashboard) names the provider in a connection failure (`FetchError.userMessage(provider:)`): "Can't reach GitHub Copilot. Tokenjar tries again at the next refresh." and "No answer from GitHub Copilot in time. Tokenjar tries again at the next refresh."; the provider-free copy below stays for the rest: "Can't find the claude command on this Mac.", "Signed out. Sign in again to see limits.", "The sign-in or API key was rejected.", "Checking too often. Tokenjar waits before the next check.", "Can't reach the server. Tokenjar tries again at the next refresh.", "No answer in time. Tokenjar tries again at the next refresh.", "Couldn't read the usage answer. An update may have changed it.", "Keychain access was denied. Tokenjar won't ask again on its own.", "Update <cli> to <version> or later.", or without a known version "Update <cli>: this version answers in a format Tokenjar can't read." A no-subscription or unsupported failure shows its own detail, such as "No Copilot access for this GitHub account" or "Update agy to 1.1.11 or later".

## Provider status

Off until turned on in Settings > General, on each Mac: the switch is `providerStatus` in Tokenjar's own preferences (`ProviderHealthSetting`, read and written through an injected store), never in `config.json`, which can be shared between Macs. While it is on, `AppModel.checkProviderHealth` asks the status summary of each provider with an account here and a feed (Claude, Codex, GitHub Copilot), once per provider, through `ProviderHealthFetcher` (one GET, no headers of its own, 10 s timeout). When it asks is in [Scheduling](#scheduling). Answers stay in memory (`AppModel.providerHealth`) until a newer one replaces them, the switch goes off or the app quits; turning it off clears them at once and drops answers still in flight, and turning it on asks nothing until the next popover open or refresh.

Only watched components count, by id, never the page-wide status, which on status.claude.com reflects every product on the page: Claude Code, claude.ai and the Claude API; every component of OpenAI's Codex group plus Codex in ChatGPT Desktop and ChatGPT's Login; GitHub's Copilot, not Copilot AI Model Providers. An unresolved incident that lists a watched component that is down is one item titled by the incident; watched components down with no incident listing them are one item together, titled by a component-less incident only when that incident names one of them. On Claude and Copilot, an unresolved incident filed with no components shows as an "Incident" item when its name or an update names the product and its impact is not none. A component under maintenance takes the name of the maintenance in progress that lists it. Items read worst first: major outage, partial outage, degraded performance (and statuses this build does not know), incidents, maintenance; newest first within a level. An answer is dated by its arrival less its `Age` header, so a copy a CDN kept shows its age; `Date` counts only when `Age` is missing, since it is read against this Mac's clock.

A failed check (no answer, an HTTP error or redirect, or a body that does not decode, which is a parse failure rather than "all fine") keeps the last answer and changes nothing on the cards, the header, connectivity, any account or the menu bar. It writes one unified log line (category `provider-status`, a notice, or an error for a body that does not decode), and the line under the switch in Settings says what the last check of each provider got. A status answer never lifts the offline hold.

## Information layout

## Charts and verdicts

- **Severity** is one scale for every surface: accent color while healthy, orange for a warning, red for critical. A window is a warning at `warnAt` or when it is projected to run out (the amber rule above), and critical at `criticalAt`. A window whose reset time has passed is healthy until the next check replaces its number.
- **Verdict.** Every window with a pace and at least 1 % used gets a kind: "Limit reached, resets in ..." at 100 %, "Runs out ~40m before reset" under the amber rule, "Ahead of pace +N%" or "Under pace -N%" outside a 5-point band, else "On pace". The card shows the most urgent kind, then among run-outs the longer lockout before the reset, then the higher severity, then the higher used %. A run-out or full verdict is at least a warning, so a "Runs out" or "Limit reached" line always has an orange or red icon. Other verdict lines stay gray, so a bar can be orange at `warnAt` while the line reads "On pace". Dashboard tiles show their own window's verdict, except for a full window.
- **Burn-up chart.** Used % over the current cycle against an even-pace diagonal from 0 at the cycle start to 100 at the reset. It shows the window the verdict judges when that window lasts a day or more, else the weekly window, else the longest. Samples whose own reset belongs to the previous cycle are left out, the line ends at the live value, and the chart is drawn only once its points span a tenth of the cycle and reach 1 %. A faint rule marks 100 %. Under the plot each whole day of the cycle is named ("Tue 13"), every nth day when more than eight would not fit, with a faint grid line at each midnight. Hovering shows the time and the used % at that point. A window at its limit also gets a band from now to the reset, labelled Blocked when it is wide enough.
- **Limits over time.** One line per window for one account. For All, one line per account: its tightest window among those long enough to draw as a line at that range, else its tightest. Dashed rules in amber and red mark the warn and critical thresholds, each labelled inside the plot with its level alone ("80%"; VoiceOver hears "Turns amber at 80%"), faint vertical rules mark resets, and a window with more than 12 resets in view drops its markers. A window with more than 12 cycles in the range (a 5-hour window at 7d or 30d) draws one dot per cycle, its peak, instead of a line. Samples are thinned to the peak of each 30-minute (7d) or 2-hour (30d) bucket plus the latest one, and a line breaks across a gap in sampling. The limits and spend charts share their day axis, so a date sits at the same x in both; while the history is newer than the range, the limits axis starts where it does and the subtitle says since when.
- **Colors.** Each account keeps one color slot in both dashboard charts, in config order with accounts that report windows first, so a spend-only account never leaves a gap between lines.
- **Daily spend** keeps the 6 costliest groups and folds the rest into "Other", unless only one group would fold. Models with usage but no price and no recorded cost are listed under the chart.
- **Daily tokens.** The last option of the Daily spend picker, Tokens, stacks each day's tokens by kind (`DashboardMath.tokenMix`), priced or not: cache reads at the base, then cache writes (5-minute and 1-hour together), uncached input, and output on top, each in a fixed color. ## Pace

Linear since window start. `elapsed = window - (resetsAt - now)`, `expected = elapsed / window * 100`, `rate = used / elapsed`, `eta = (100 - used) / rate`. Hidden until 5 % of the window has elapsed, and for windows that have not started, report no length or reset time, or reset in the past or more than one window away. The "Runs out" verdict, the amber color and the projected-exhaustion alert all need at least 50 % used, at least 10 % elapsed and `resetsAt - now - eta` of 15 minutes or more.

With working days (`paceDays: workingDays`), a window longer than a day counts only working days: `elapsed` and `window` become the working time in them, and the ETA is walked forward over working days, so a weekend adds clock time but no use. The weekend is the region's, from Foundation's calendar (Saturday and Sunday in most regions, Friday and Saturday in some). Expected % is the working time elapsed over the window's total working time, so it reaches 100 % when the last working hour before the reset ends and stays there through a trailing weekend, stays at 0 % through a leading one, and never jumps when a weekend starts. With no working time left, nothing more is projected to be used, so a weekend starting never makes a window run out. Only a window with no working time at all counts every day, and windows of a day or less always count every day. `Pace.compute(workWeek:)` takes a `WorkWeek`; no caller passes one in this build, so every surface, `--status` included, counts every day.

## Alerts

Projected exhaustion, window reset, early reset and source problem alerts each have a toggle under `alerts` (`projectedExhaustion`, `earlyResets` and `sourceProblems` on by default, `windowResets` off); `alerts.enabled` turns every alert off. Early resets are on by default because they are rare and only ever good news: there is room again sooner than the countdown said. A plain reset is expected and on schedule, so it stays opt-in.

- Threshold crossings, default 80 % and 95 % used, per window; an account can set its own (`alertThresholds`). Only the highest newly crossed threshold fires, and it withdraws the lower one's notification. Dedupe key is account, window, cycle and threshold; the cycle is the reset time rounded to 10 minutes when first seen (the poll time for a window with no reset time). A new cycle starts when the reset time jumps forward by more than half the window or used % drops by 30 points or more; it withdraws the old cycle's notifications and re-arms every alert for that window.
- Projected exhaustion, once per cycle, when the window is at least 50 % and below 100 % used, at least 10 % elapsed, and the ETA is 15 minutes or more before the reset.
- Window reset, only when the last used % Tokenjar saw before the reset was 80 % or more.
- Early reset, when a provider starts a window over well before its scheduled reset: a new cycle (as above) seen while the old reset time was still an hour or more ahead. The hour absorbs clock skew between the Mac and the provider and reset times rounded to the hour, and a reset less than an hour early is not news. It is announced only when the next sample still reads as a new cycle against the old reading, so one sample that bounces back (a lagging replica, a zero read) is not an early reset, and a provider's saved copy never starts or confirms one. Once per reset; it withdraws the plain reset notice for the same reset, and one first seen on a baseline poll is recorded silently. A reset time that only moves earlier with usage unchanged is a reschedule, not a reset. Text: "Week limit reset early · now at 3% · next reset Thu 09:00".
- Source problem (CLI missing, signed out, no subscription, credential rejected, Keychain access denied, unreadable output, unsupported CLI, a CLI too old to read, a probe that spent tokens or quota), once per failure episode, withdrawn on the next success. Network errors, timeouts and rate limiting never open an episode. No emails, ids or raw errors in the text.
- Not-started windows never fire a threshold or projection. They can still get a reset or early reset alert, because OpenCode Go reports a window that just reset as not started. Windows whose reset time has passed are skipped.
- An account's first successful poll after launch, and any failure before it, only record a baseline. The one exception is a probe that spent tokens or quota (the Claude or agy model-turn error): it notifies at once, before any baseline, because the latch stops further probes and there would be no later chance to say so. It still needs `alerts.enabled` and `alerts.sourceProblems`, and it is still once per episode, so an account with a source problem already open, even since before a relaunch, gets no new notification. A run of network errors or timeouts does not open one.
- With alerts off the state is still tracked, so turning them on does not replay old crossings. State persists in `alert-state.json` (everything except the baseline set and early resets waiting for their confirming sample), written only when an evaluation changed it, so a restart does not repeat alerts.

Delivery: notification ids are the dedupe keys, so a repost replaces instead of stacking, and notifications are grouped per account. A click on a notification, or its "Open Dashboard" action, opens the dashboard on that account. With alerts on, the app asks macOS only for quiet provisional delivery (no prompt), at launch and when alerts are turned on. The system prompt for banners appears only from "Allow Banners" in Settings > Alerts. Notification Center serves only an app bundle, so a binary run from `.build` cannot post at all.

## Probe latch

`claude -p /usage` and `agy -p /usage` are meant to answer locally. If one runs as a model turn instead, the fetcher throws that CLI's model-turn error, and `ProbeLatch` records the account in `probe-latch.json` with the CLI and a fingerprint of its binary (SHA-256 of the resolved path, size and modification date). gh's GET cannot start a model turn, so a Copilot account is never latched.

- Claude: the read stops at the first `assistant` line with `usage_report` (the answer) or the first `result` line with `num_turns` or `total_cost_usd` above 0 (a model turn). If it reaches the end without either, any `assistant` line that carried neither `usage_report` nor `local_command_run` makes the run a model turn. A run that times out or exits without a result line after such a line fails the same way, with no cache fallback. A timeout after only the local `/usage` answer is a plain timeout with the cache fallback.
- Antigravity: a top-level `response`, `stats` or `num_turns` in the output of a run that exited 0, when that output has no `groups`, no `error` and no `data.message`. agy prints a local command's answer in that same envelope, so `num_turns` 0 beside a `command` object, with no `stats` and no `usage` count above 0, does not latch.
- A latched account is skipped by every path: ticks, wake, popover open, the refresh button, Retry, Settings' Check Now, and a relaunch, since the file persists. Its card shows the latching CLI's message ("Claude Code ran /usage as a prompt, which spends tokens. Checks for this account are paused until claude updates or you click Try Once More.", or the Antigravity one).
- It is released when that CLI's binary fingerprint changes (a claude update never releases an agy latch, or the reverse), or by `AppModel.retryProbe(accountID:)`, which runs one check and latches again if it repeats. The popover's and Settings' Try Once More call it; Disable sets the account's `enabled` to false.

## Config and sync

`~/.config/tokenjar/config.json` (`$XDG_CONFIG_HOME/tokenjar/config.json` when that variable is set in the app's own environment) holds non-secret settings: `version`, `refreshMinutes`, `menuBar` (`mode`, `icon`, `warnAt`, `criticalAt`, `showResetCountdownWhenFull`), `alerts` (`enabled`, `thresholds`, `projectedExhaustion`, `windowResets`, `earlyResets`, `sourceProblems`), `cliPaths`, `launchAtLogin`, `paceDays`, and `accounts` (`id`, `provider`, `label`, `enabled`, `profileDir`, `credential`, `showInMenuBar`, `refreshMinutes`, `alertThresholds`, `dashboardURL`). Every field but an account's `id` and `provider` may be left out and takes its default. It is safe to stow from the dotfiles repo. Check provider status pages is not in it: that switch is a preference of each Mac.

- **Providers.** `provider` is one of `claude`, `codex`, `opencode-go`, `opencode-zen`, `antigravity`, `copilot` and `devin`. Config files hold these raw values, so they are permanent. `profileDir` is `CLAUDE_CONFIG_DIR` for Claude, `CODEX_HOME` for Codex, `GH_CONFIG_DIR` for GitHub Copilot, and opencode's data folder for OpenCode.
- **Menu bar icon.** `menuBar.icon` is one of `app`, `mark:mana`, `mark:taper`, `mark:tally`, `mark:burnrate`, `mark:genio`, `logo:claude`, `logo:openai`, `logo:antigravity`, `logo:copilot`, `logo:opencode`, `logo:windsurf`, `symbol:sparkles`, `symbol:brain`, `symbol:cpu` or `symbol:gauge.with.needle`; the default is `app`. A missing key, `null`, or a string this build does not know reads as `app`, so a value from a newer build does not fail the load on an older one; a value that is not a string is a load error like any wrong type. Because a save rewrites the whole file from decoded values, an older build that saves any Settings edit writes `app` over an icon it does not know.
- **Thresholds.** `alerts.thresholds` (default `[80, 95]`) applies to every window, and an account's `alertThresholds` replaces it (`AppConfig.thresholds(for:)`). An empty list turns threshold alerts off.
- **Keys no longer read.** Earlier builds decoded `hotkey`, `alerts.shortThresholds`, and an account's `shortAlertThresholds` and `creditAllowance`, and nothing read them. This build does not decode them: a file that holds them loads as before, and a save keeps them as it keeps any key this build does not read (see Save).
- **Pace days.** `paceDays` is `everyDay` (the default) or `workingDays` (see Pace). A missing key, `null`, or a string this build does not know reads as `everyDay`; a value that is not a string is a load error like any wrong type. It has no Settings control. It does not change pace; set to `workingDays`, it only spreads a recommended daily budget over the working days left.
- **Merge.** `config.local.json` next to it holds machine overrides and wins on merge. The merge is deep. `accounts` merge by `id`, field by field, and a local entry with a new id is appended. When `config.json` has no `accounts`, the local list merges onto an empty one, so a local id listed twice always becomes one account.
- **Hidden accounts.** An enabled account shows only when what it reads exists on this Mac: the profile dir (default `~/.claude` or `~/.codex`) for Claude and Codex, gh's config folder (`profileDir`, else `~/.config/gh`; checked for existence only, never opened) for GitHub Copilot, for OpenCode Go the credential file, else the default `auth.json` (`$XDG_DATA_HOME/opencode/auth.json` or `~/.local/share/opencode/auth.json`; an OpenCode Go `profileDir` is not checked), and for OpenCode Zen the `opencode.db` its fetcher reads (in its `profileDir`, else `$XDG_DATA_HOME/opencode` when that variable holds an absolute path, else `~/.local/share/opencode`), whatever credential first run gave it. A pasted Keychain key, Antigravity and Devin have no file to check and always show. One shared file therefore works on every Mac. The check runs on every tick, so a folder that appears or goes away shows up within 30 seconds.
- **Save.** Settings edits only `config.json`, never `config.local.json`. A save copies the leaf fields the user changed onto `config.json` as last read, so a value `config.local.json` overrides on a setting or on an account that is in `config.json` never leaks into the shared file, and accounts that exist only in `config.json` are kept. An account that exists only in `config.local.json` is never written to `config.json`: it always loads after the shared accounts, and a Settings edit to it lasts only until the next load, so change it in `config.local.json`. The file is rewritten whole, defaults included, pretty-printed with sorted keys, except that keys this build does not read (a newer build's, from another Mac) are kept as they are, at any depth and in each account still present, matched by `id`. Builds from before this rule drop them on save, so every Mac that shares the file should run the same build. An edit whose save fails is undone and the banner says so.
- **Symlinks.** A `config.json` that is a symlink is written through its real target, resolved with `realpath`: a relative stow link resolves against the link's own folder and chains are followed, so the link survives. Every Settings edit first checks both files, so a link whose destination is missing is caught there: the app keeps its settings, saves nothing and shows "config.json is missing or its link is broken". `ConfigStore.write` also refuses such a link: it throws `ConfigError.brokenLink`, writes nothing and keeps the link. Any write that fails shows "Could not save config.json."
- **Load errors.** An unreadable file, invalid JSON (merge-conflict markers, a wrong type) or a top level that is not an object in either file throws `ConfigError.invalidJSON` naming that file; its `detail` is a raw decoder message and is never shown. Two accounts with the same `id` in `config.json` throw `ConfigError.duplicateAccountID`, because a save matches accounts by `id`, so an edit to the second would be written over the first one's provider and unknown keys. (In `config.local.json` a repeated `id` merges into the first entry; see Merge.) Its `userMessage`, such as `config.json lists two accounts with the id "claude-2". Rename one.`, replaces "Could not read config.json." in the banner and in `--status`, since the JSON itself is valid. The app keeps the settings it last loaded (none, when the load at launch fails), shows "Could not read <file>. Using the last good settings, and nothing is saved until it is fixed and reloaded." ("No settings are loaded" in place of "Using the last good settings" when nothing has loaded yet), and saves no edit until a load succeeds. A `config.json` that goes missing while the app runs, or a stow link whose target is gone, keeps the current settings the same way.
- **Reload.** Each tick compares the modification dates of both files (through symlinks) and reloads on a change, for example after a `git pull` in the dotfiles repo. Every Settings edit checks the same first, so an outside change is the base of the edit instead of being reverted. Settings > General > Reload loads on demand.
- **First run** happens only at launch, and only when nothing at all, not even a dangling stow link, is at the config path. It writes default settings plus the accounts discovery finds: `~/.claude` (labelled Work for a Team or Enterprise `oauthAccount.organizationType` in `~/.claude.json`, else Personal), `~/.codex/auth.json` (existence only), the `opencode-go` and `opencode` entry names in opencode's `auth.json` (Zen is added with `showInMenuBar: false`), `agy` on the CLI search path, `gh` on the CLI search path (located, never run; id `copilot`, label GitHub), and any of `Devin.app` or `Windsurf.app` in `/Applications` or `~/Applications`, or `~/Library/Application Support/Devin` or `Windsurf` (existence only; id `devin`, `showInMenuBar: false`). CodexBar's settings are never read at first run. An account added in Settings starts with `showInMenuBar` off when its provider reports no windows (OpenCode Zen, Devin).
- **CodexBar import.** Settings > General > Import from CodexBar reads CodexBar's enabled providers, global warning thresholds (CodexBar stores % remaining, Tokenjar % used), refresh interval and notification toggle, lists the changes, and applies them only when the user confirms. CodexBar's `copilot` maps to GitHub Copilot, and `devin` and `windsurf` to Devin. A discovered account matches a configured one of the same provider and the same location: the same profile folder (gh's config folder for Copilot), credential file, or `opencode.db` for Zen; Antigravity and Devin are one login per Mac.
- **CLI paths.** `cliPaths` maps a CLI name (`claude`, `codex`, `agy`, `gh`, and `opencode`, which only the sign-in command uses) to an absolute path. When one is set and that path is an executable on this Mac, it is used. Otherwise a fixed list of folders is searched, never through a login shell, so an entry set on another Mac that shares the file does not make the CLI missing here.

## Storage

`~/Library/Application Support/Tokenjar/` is created, or tightened if it exists, at 0700. `tokenjar.sqlite` in it is created 0600 before SQLite opens it and uses WAL; its `-wal` and `-shm` files take the same mode. `schema_version` records which entries of `SQLiteUsageStore.migrations` have run. Migrations are append-only, and a database newer than the build is refused.

- `snapshots(account_id, fetched_at, json)`: the latest `UsageSnapshot` per account, shown at launch until the first fetch lands.
- `window_samples(account_id, window_id, ts, used_percent, resets_at)`: one row per fetch per window. A sample identical to the previous one (for a not-started window, the same used %) and less than an hour newer is not written; the last one skipped is held in memory and written just before the window's next change, so a flat run keeps its end. An hour is under the dashboard's 2-hour sampling gap, so an idle window's line stays whole. Rows older than 180 days are pruned on the first successful fetch after launch and then at most once a day.
- `usage_events(dedupe_key, ts, account_id, harness, model, project, input, output, cache_read, cache_write_5m, cache_write_1h, reasoning, reported_cost, web_search_requests)`: one row per model response, upserted by `dedupe_key` keeping the larger value of each count, and committed in chunks. `dedupe_key` is the SHA-256 hex digest of the raw key (`claude:<message.id>:<requestId or sessionId>`, `codex:<response_id>`, `codex:<rollout file name>:<cumulative total>`, `codex:<rollout file name>:@<byte offset>`, `opencode:<message id>`). `project` is the last path component of the working directory, `~` for the home folder itself, in all three scanners. A Claude Code worktree (`<repo>/.claude/worktrees/<name>`) or a tool folder inside a repo (`<repo>/.superpowers/sdd/<plan>`) counts as `<repo>`; hidden folders directly under home keep their own name. Raw events rather than rollups, because Claude Code deletes transcripts after 30 days and writes a response on several lines while it streams. Daily totals per local day, account, harness, model and project are computed at query time. The upsert never changes `model` on a conflict.
- `scan_state(scanner, account_id, path, value)`: one checkpoint per log file (Claude, Codex) or per opencode table. `path` is the SHA-256 hex digest of the file path, or of `<opencode.db path>#<table>` for opencode. `value` is `<inode>:<offset>` for Claude, a JSON object with inode, offset and running context (last cumulative totals, model, project) for Codex, and the largest `time_updated` read for opencode. A scan rewrites all of an account's checkpoints for that scanner, and only when at least one of them moved.

Migration 2 rewrote every `dedupe_key` an earlier build stored raw into its digest and cleared `scan_state`, which costs one full rescan that merges into the rehashed events. `StoredIdentifierTests.scannedPathsAndResponseIDsAreStoredOnlyAsDigests` runs the real scanners into a real store and checks that the database bytes, WAL included, hold neither the home folder path nor a raw session id.

Migration 3 added `web_search_requests` (0 for every row already stored) and cleared the `claude-transcripts` checkpoints, so transcripts still on disk are read once more and their web search counts merge into the events already stored.

Next to the database: `alert-state.json` (fired dedupe keys, failing accounts, and the last reset time, used % and cycle per window) and `probe-latch.json` (`{"entries": {"<account id>": {"binary": "<sha256>", "cli": "claude"}}}`, with `cli` either `claude` or `agy` and an entry without `cli` read as claude). Both are written atomically and set to 0600 after the support folder is tightened to 0700.

## Pricing

`Resources/pricing.json` maps model ids to USD per million tokens (input, output, cache read, cache write 5m, cache write 1h) and, optionally, USD per 1,000 server-side web searches (`webSearchPer1k`), with the source URL and date for each entry. `~/.config/tokenjar/pricing.json` overrides it: each model or alias there replaces the bundled entry of the same id whole, and a file that declares another version, currency or unit is ignored. Costs are labelled "API-equivalent estimate".

The same file has `plans`: the US monthly list price of a subscription plan (`monthlyUSD`), keyed by provider id and then by the plan label the fetchers produce, each with its source URL and the date it was read. The override replaces plans one by one, and may hold `plans` without `models`. The bundled table holds Claude Pro, Max 5x, Max 20x, Team and Team Premium (per seat), Codex Go and Plus, and OpenCode Go. It leaves out a label that stands for more than one price (Claude's `Max` with no tier, Codex's `Pro`, which collapses the $100, $200 and $500 tiers, Codex's `Business`, whose seat type the plan type does not give) and plans with no single list price (Free, Edu, Enterprise). GitHub Copilot and Antigravity keep no local logs, so they have no spend to compare.

- Lookup is the exact id, then an alias, then the normalized id and its alias. Normalizing lowercases the id and drops a `vendor/` path, a Bedrock `[region.]anthropic.` or `openai.` prefix, a `-v1:0` style suffix, a Vertex `@date`, a `[1m]` tag and a trailing release date. Any other id is unpriced rather than borrowing a similar id's price (`gpt-5.5-pro` costs six times `gpt-5.5`); an alias in the override file maps it.
- Claude Haiku 5.5 bills every token of a request at a higher rate once its prompt (input plus cache reads plus 5-minute and 1-hour cache writes) is over 100,000 tokens. `PriceTable.billedModel` records such a request as `claude-haiku-5-5>100k`, Bedrock and Vertex spellings included, and the price table prices that id at the long-prompt rate. It shows as its own model in the by-model split. Events stored before this rule keep `claude-haiku-5-5`.
- A Claude response whose `message.usage.speed` is `fast` ran in fast mode, which has its own input and output rates with the prompt caching multipliers on top. `PriceTable.billedModel` records it as the normalized id plus `+fast` (`claude-opus-5-5+fast`), and the price table prices `claude-opus-5-5+fast` and `claude-opus-5+fast`; any other model's fast requests are unpriced rather than priced at the standard rate. It shows as "(fast mode)" in the by-model split. Events stored before this rule keep their standard id, since the upsert never changes `model`.
- `message.usage.server_tool_use.web_search_requests` is stored per response and priced at the model's `webSearchPer1k`. A model without that field (every OpenAI entry, and any override entry that leaves it out) adds nothing for its web searches.
- Rows whose harness recorded a cost (opencode) keep that cost and are not repriced; only tokens without a recorded cost are priced.

## Distribution

`make install` builds from source with `swift build -c release`, assembles `Tokenjar.app` (Info.plist with `LSUIElement`, bundle id `com.pedromosquera.tokenjar`, version from `VERSION`; the committed `Resources/AppIcon.icns`, `Resources/Logos/`, `Resources/Marks/`, `Resources/pricing.json`, `LICENSE` and `THIRD_PARTY_NOTICES.md` copied in), fails if the binary links an `@rpath` library, clears extended attributes, signs it ad-hoc with the hardened runtime, copies it to `~/Applications` and launches it. `Scripts/make-icon.sh` rebuilds the `.icns` from `Resources/AppIcon.svg` with `sips` and `iconutil`; run it by hand after editing the SVG. No admin rights, no quarantine, no Gatekeeper prompt. The linker gets `-platform_version macos 14.0 26.0` so the binary is stamped with a real SDK version (SwiftPM's default build system stamps the deployment target, which makes macOS run the app in compatibility mode).

**Homebrew.** A formula, `tokenjar.rb` at the root of [PedroMosquera/homebrew-tap](https://github.com/PedroMosquera/homebrew-tap), builds the same app on the user's Mac from a release tag's source archive. It runs `make app SWIFT_FLAGS="--disable-sandbox --manifest-cache local"` with network access denied: SwiftPM's own sandbox cannot run inside Homebrew's build sandbox, and the local manifest cache keeps the build out of `~/Library/Caches`. It installs `Tokenjar.app` into its keg and links one command into `bin`, `tokenjar-install-app`, which runs the keg's copy of `Scripts/install.sh` with `TOKENJAR_APP` set to the keg's app. Homebrew's sandboxes cannot write to `~/Applications`, so the copy has to happen after `brew` is done. Running the same script as `make install` means both paths quit, replace, verify and open the app the same way and at the same path, and a change to `install.sh` reaches both. The script checks that the app it copies exists before it quits or deletes anything, and `make install` clears `TOKENJAR_APP`, so it always copies its own build. The formula's caveats tell the user to run `tokenjar-install-app` after each install, upgrade and reinstall. The Tokenjar binary itself is not linked into `bin`, because started with no flags it is the full app. The archive has no `.git`, so a Homebrew build's `CFBundleVersion` is 1, lower than any `make` build's; a `make` build left registered elsewhere can win when macOS picks the app by bundle id, so switching to Homebrew means `make clean` in the clone. The formula requires macOS 15 (`depends_on macos: :sequoia`): Swift 6.2 needs macOS 15.6, and Homebrew can only name a release. [development.md](development.md#releasing) has the release steps.

**Renamed from Headroom.** Builds before the rename were Headroom, bundle id `com.pedromosquera.headroom`. macOS treats the new bundle id as a new app, so notification permission, the launch at login registration and saved window frames start fresh. API keys pasted in Settings stay under the old Keychain service, `com.pedromosquera.headroom.apikeys`, which the app never reads (hard rule 2), so they are pasted again. `Scripts/install.sh`, which `make install` and Homebrew's `tokenjar-install-app` run, first quits and deletes `Headroom.app` in the install folder, only when its Info.plist names exactly `com.pedromosquera.headroom`; it waits up to 5 seconds for the app to exit and stops without installing if it is still running. History and config move once: `AppModel.loadState` runs `LegacyMigration` before it opens the config or the database, and the developer flags never reach it. It renames `~/Library/Application Support/Headroom` to `Tokenjar` and `~/.config/headroom` (or `$XDG_CONFIG_HOME/headroom`) to `tokenjar` when the new name does not exist yet (a Tokenjar support folder holding only the empty `probe` folder that `--probe` creates counts as absent and is removed with rmdir), then renames `headroom.sqlite` and its `-wal` and `-shm` files to `tokenjar.sqlite*` as one set, putting them back if one rename fails. A rename in place keeps a stow link inside the config folder, or a config folder that is itself a stow link, resolving. When both names exist nothing changes, and nothing moves while an app with the old bundle id, or a process named exactly `Headroom` (the `pgrep -x` match install.sh makes), runs. The move never renames onto a taken name, so while `LegacyMigration.hasDataToMove` still holds afterwards (Headroom runs, or a step failed), `loadState` opens neither the config nor the database and `loadConfig` does nothing for the rest of that launch; the banner says to quit Headroom, or that the move failed, and the next launch tries again. This also covers `make run`, which does not quit Headroom first. A failure is logged and never stops the launch. [privacy.md](privacy.md#renamed-from-headroom) lists exactly what moves.

Constraints found while packaging:

- No `.xcassets` or `.xcstrings` (they need Xcode). Logos and marks ship as SVG in `Contents/Resources/Logos` and `Contents/Resources/Marks` and load with `NSImage(contentsOf:)` through `Bundle.main`, never `Bundle.module`; a binary run from `.build` falls back to the repo's `Resources/`.
- Command Line Tools ship no SwiftUIMacros plugin, so views avoid the `@State` macro: they use explicit `State` storage, the `SettingsState` alias or an `ObservableObject`.
- Notifications and launch at login work only from an app bundle; use the installed copy in `~/Applications`.
- Ad-hoc signatures change on every build, so Keychain grants for the app's own item re-prompt after a rebuild, and a Deny is not remembered. Only pasted API keys live there, and each is read once per launch (see [Scheduling](#scheduling)).
- On a Mac that only runs allowlisted binaries, every new ad-hoc build needs allowlisting before it launches.

There is no prebuilt app: no release zip and no cask. Both `make install` and the Homebrew formula build on the user's Mac, so the app is never quarantined and needs no Developer ID.
